# Domain contexts and registration

AiContext owns a Lazy<DefinitionCatalog> initialized with ExecutionAndPublication and a separate active-catalog reference. The lazy catalog holds the original registered contracts. OnConfiguring runs once on the first catalog access, including Validate, Compose, ExportDefinitions, ApplyDefinitions or conversation creation; it never runs from the base constructor before derived properties initialize. Initialization errors remain cached. Derived contexts must not recursively access their own catalog from OnConfiguring.

AiContextBuilder registers AiRole, AiRule, AiRuleSet and AiContextDefinition references in separate ordinal-ID dictionaries. Repeating the same reference is idempotent. Different objects with the same ID within a category fail. Rule-set registration validates all rules before changing any dictionary, so a caught conflict leaves no partial registration.

Build copies dictionary values into immutable arrays and captures compiled content in an AiDefinitionSnapshot. An escaped builder cannot change a published catalog. Definitions expose nonvirtual get-only base properties; application subclasses should also remain immutable. AiContextDefinition holds reusable Untrusted data and provenance; instructions belong in roles/rules or explicitly supplied Trusted values.

Selection uses reference identity, not Equals overrides or mandatory string lookup. Reusing a definition across domains requires explicitly registering that reference in both catalogs. Generic WithRole<T>, WithRule<T>, WithRules<T> and WithContext<T> selection requires exactly one registered object assignable to T; zero or multiple matches raise ArgumentException. Published content replacements retain those original CLR references.

DomainId defaults to the assembly simple name plus full context type name, without assembly version. Applications may override it with a non-empty stable ID for persisted domains. Build validates the ID and captures its value; applications should keep the override stable for the context lifetime and across compatible deployments. Definition IDs are ordinal and scoped by domain and kind. History eligibility compares DomainId values, so different context types can deliberately share a domain ID. Instance identity and domain identity are not tenant/security boundaries. OnConfiguring should be deterministic for compatible instances.

ExportDefinitions returns the current immutable declarative content. ApplyDefinitions validates a complete snapshot against the original registration through DefinitionSnapshotResolver, then publishes a replacement with Interlocked.Exchange. Catalog reads use Volatile.Read and fall back to the lazy original. Successful concurrent updates use last-publication-wins semantics per context instance. Failed updates leave the active catalog unchanged; updating one context does not update another instance with the same DomainId.

Registered objects continue to expose compiled defaults after an update. New composers capture active content at Compose time; existing composers and conversations retain their captured catalogs. Conversation adoption requires explicit RefreshDefinitions or UseContext. Refresh checks a preserved ContractIdentity token and requires the original context instance, even when another instance has matching IDs or shared definition references. See [Definition serialization and updates](DefinitionSerialization.md) and [Conversation state](ConversationState.md).

AddAiContext registers contexts as singletons; AddAIComFramework registers the conversation factory and validation pipeline as scoped and the default untrusted renderer as singleton. Context constructor dependencies must therefore be singleton-safe. Validate can be called at application startup to surface configuration failures early. Contexts do not retain scoped validators or own model-client lifetimes.
